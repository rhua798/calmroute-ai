# 安心领航 CalmRoute AI — PRD v1.0

| 字段 | 内容 |
| --- | --- |
| 产品阶段 | 概念验证 / 可用性测试前 |
| 核心场景 | 上海至莫干山多目的地自驾 |
| 版本 | 1.0 |
| 文档状态 | Draft |

## 1. 产品背景

导航产品已能稳定完成地点搜索、路线计算和转向引导，但真实自驾还包含接人、补能、用餐、停车和时间窗口等多重约束。当路况、排队或目的地状态变化时，用户需要跨多个服务重新拼装决策。

安心领航希望把导航从“被动路线引导”扩展为“持续管理出行不确定性的主动助手”。

## 2. 产品目标

### 2.1 用户目标

- 用一次表达说清多目的地、时间、偏好与电量约束。
- 在行程风险真正发生影响前获得提醒。
- 快速理解备选方案的优劣和推荐理由。
- 在驾驶中以最少的注意力完成确认。

### 2.2 业务/产品目标

- 验证“可解释主动建议”是否能提升建议接受率。
- 验证跨屏分工是否能缩短复杂路口的决策时间。
- 建立可追踪的主动建议漏斗和导航质量指标。

### 2.3 非目标

- v1.0 不自研路线计算或高精地图能力。
- v1.0 不用大模型直接生成道路或预测电量。
- v1.0 不在真实动态驾驶中进行未经安全评审的实验。
- v1.0 不覆盖所有城市出行服务。

## 3. 目标用户

### 核心用户

有新能源汽车自驾经验、偶尔进行周边游，需要同时考虑同行者、补能、用餐和抵达时间的用户。

### 次要用户

- 对陌生城市和复杂道路缺乏信心的新手司机。
- 经常为家庭或朋友组织自驾行程的主计划者。

## 4. 待验证问题假设

1. 用户愿意用少量绕路换取更可信的时间和补能结果。
2. 推荐方案中同时呈现“影响+理由”，能提升理解率和接受率。
3. 用户对主动服务的容忍度取决于风险紧迫性，低影响事件不应打断。

## 5. 核心场景

### 5.1 初始需求

> 周六上午从上海出发，先去虹桥接朋友，再去莫干山。中午想吃当地菜，剩余电量不能低于 20%，晚上 7 点前到民宿。

### 5.2 行程事件

系统检测到原计划的安吉服务区预计排队 18 分钟，需要在不影响抵达时间和安全电量的前提下提供替代方案。

### 5.3 理想体验

1. 提前说明已检测到的风险。
2. 告诉用户推荐的下一步。
3. 对比原方案和新方案的时间、里程和电量影响。
4. 允许通过中控或语音一步确认。
5. 确认后同步更新后续行程和预期。

## 6. 功能需求

### P0：概念验证必须完成

| ID | 需求 | 说明 |
| --- | --- | --- |
| F01 | 自然语言行程输入 | 识别目的地、时间、偏好、电量和同行者约束 |
| F02 | 结构化行程生成 | 生成可编辑的途经点、时间和服务节点 |
| F03 | 行程风险检查 | 检查抵达时间、电量、排队、停车和道路风险 |
| F04 | 备选方案生成 | 当风险超阈值时生成至少一个可行方案 |
| F05 | 可解释对比 | 展示方案对时间、里程、电量和风险的影响 |
| F06 | 一步确认/拒绝 | 中控按钮和语音支持简单确认 |
| F07 | 跨屏同步 | 根据屏幕职责更新 AR-HUD、仪表和中控信息 |
| F08 | 事件埋点 | 记录曝光、查看理由、接受、拒绝和撤销 |

### P1：下一阶段

- 多轮修改行程约束。
- 充电和停车服务预约。
- 基于用户历史选择的偏好记忆。
- 对同行者分享行程和变更。

## 7. Agent 与技术边界

### 7.1 能力分工

| 层级 | 职责 |
| --- | --- |
| 大语言模型 | 需求理解、任务拆解、工具编排、自然语言解释 |
| 地图服务 | POI 搜索、路线计算、时间和距离 |
| 车辆数据 | 剩余电量、续航与能耗预测 |
| 出行服务 | 充电桩、停车场、餐厅等状态 |
| 规则引擎 | 安全约束、打断阈值、方案可行性和排序 |

### 7.2 主动打断原则

只有在以下至少一项显著恶化时才主动打断：

- 安全风险。
- 抵达时间违约风险。
- 剩余电量低于安全阈值。
- 已计划服务不可用。
- 可行备选方案的收益明显高于切换成本。

## 8. 跨屏信息策略

| 触点 | 主要任务 | 允许信息 | 限制 |
| --- | --- | --- | --- |
| AR-HUD | 立即执行 | 当前车道、转向动作、高紧迫风险 | 一次只有一个主动作 |
| 仪表 | 维持预期 | 下一步、距离、电量、ETA | 不提供复杂方案对比 |
| 中控 | 全局决策 | 行程、方案对比、理由、服务 | 驾驶中避免多步输入 |
| 语音 | 免手确认 | 结论、关键理由、接受/拒绝 | 默认一句话说清 |

## 9. 数据埋点

| 事件 | 触发时机 | 关键属性 |
| --- | --- | --- |
| `trip_plan_created` | 首次生成行程 | 目的地数、约束数、生成耗时 |
| `risk_detected` | 风险达到规则阈值 | 风险类型、影响、紧迫等级 |
| `suggestion_exposed` | 用户首次看到建议 | 建议类型、展示屏幕、展示时机 |
| `reason_viewed` | 用户展开详细理由 | 停留时间、理由层级 |
| `suggestion_accepted` | 接受方案 | 决策耗时、方案收益 |
| `suggestion_rejected` | 拒绝方案 | 决策耗时、拒绝原因 |
| `suggestion_undone` | 接受后撤销 | 撤销间隔、撤销原因 |
| `navigation_outcome` | 行程节点完成 | ETA 误差、电量误差、是否重规划 |

## 10. 核心指标

| 指标 | 计算方式 | 探索性目标 |
| --- | --- | ---: |
| 复杂路口决策时间 | 正确理解引导所需的平均时间 | ≤ 3.0 s |
| 建议理解率 | 能正确复述推荐理由的任务数 / 全部任务数 | ≥ 85% |
| AI 建议接受率 | 接受次数 / 有效曝光次数 | ≥ 70% |
| 建议后撤销率 | 撤销次数 / 接受次数 | 越低越好 |
| ETA 误差 | 实际到达时间 - 最后一次预测时间 | ≤ 8 min |
| 主观安全感 | 5 分量表评分 | ≥ 4.2 |

## 11. 验收标准

1. 用户可通过一段自然语言生成包含接人、补能、用餐和抵达的行程。
2. 系统能将“充电站排队 18 分钟”识别为行程风险。
3. 系统提供至少一个符合时间与电量约束的备选方案。
4. 方案对比至少包含时间、里程、电量与排队影响。
5. 用户确认后，行程时间线、ETA 和确定性状态同步更新。
6. AR-HUD 不显示复杂方案对比，驾驶中中控不要求多步文本输入。
7. 曝光、接受、拒绝和撤销行为均能通过埋点追踪。

## 12. 用户研究计划

### 阶段 A：问题访谈

- 样本：5–8 名有自驾经验的新能源车用户。
- 目的：还原近期一次复杂自驾行程中的决策、情绪和工具切换。
- 产出：用户旅程、问题频率/严重度矩阵、假设修订。

### 阶段 B：可用性测试

- 样本：7–10 名目标用户。
- 任务：理解充电排队事件、对比方案、做出决策、复述推荐理由。
- 对比：基准版“只提醒”与方案版“结论+影响+理由”。
- 产出：决策时间、理解率、接受率、质性反馈与迭代清单。

### 阶段 C：静态实车演练

- 只在停驶车辆中评估信息可见性、层级和跨屏一致性。
- 不将静态测试结果宣称为动态驾驶安全性证据。

## 14. 风险与待决策项

- 缺少真实充电排队数据时，如何在 Demo 中明确区分模拟数据。
- “出行确定性指数”的子项权重如何通过研究校准。
- 主动打断阈值是否应根据驾驶阶段和用户偏好动态调整。
- 语音确认在噪声、多人对话和方言环境中的可靠性。
- AR-HUD 动效和信息层级需要哪些整车工程约束作为输入。
